# RefScope v0.8 — Adoption hardening

## Purpose

Turn a developer prototype that works for its author into a tool another kernel developer can install and trust.

This phase is primarily engineering, compatibility, documentation and external validation.

## Installation

Required:
- documented dependencies;
- reproducible build;
- release binaries where technically reasonable;
- package/container only if it genuinely simplifies use.

Do not hide kernel/BPF requirements.

At startup, capability detection must explain missing requirements.

## Supported environments

Publish an explicit matrix:

```text
architecture
kernel version/range
BTF requirement
DWARF/source requirement
fentry support
kprobe fallback
supported sanitizers
```

"No support" is better than silent wrong output.

## Stable run format candidate

Freeze a versioned schema candidate:

```json
{
  "schema": "refscope.run.v1",
  ...
}
```

Provide a JSON Schema or equivalent machine-readable definition.

## Target schema candidate

Freeze target config version:

```yaml
schema: refscope.target.v1
```

Provide validation and useful errors.

## Diagnostics reproducibility

Given:
- same saved run bundles;
- same RefScope version;

offline diagnosis must be deterministic unless explicitly using a stochastic mode.

Record algorithm version and scoring weights.

## Capture safety

Required:
- clean detach on SIGINT/SIGTERM;
- resource limits;
- max event rate;
- max object count;
- bounded stack map behavior;
- clear warning before broad probes;
- `--dry-run`;
- `--max-events`;
- timeout.

## Security model

Document:
- required privileges/capabilities;
- what kernel memory-derived data can appear in output;
- pointer redaction option for shareable reports;
- whether logs may contain sensitive process names/data.

## Performance quality gates

Publish benchmark table.

Suggested goals, not universal promises:

- zero silent event loss;
- <0.1% event loss in supported benchmark configuration;
- capture overhead low enough that target repro still triggers at a useful rate;
- memory usage bounded/configurable.

If a specific heavy target has higher overhead, document it.

## Testing

### Unit
- parser;
- target validation;
- alignment;
- scoring;
- graph model;
- symbol normalization.

### Integration
- synthetic kernel target;
- kref target;
- ref_tracker target;
- workqueue transfer;
- deliberate leak/double-put.

### Kernel matrix
Automated VM jobs for supported kernels/architectures.

### Regression cases
Real bug cases must remain reproducible where practical.

## Error messages

Every common failure should explain the next action.

Bad:

```text
attach failed -22
```

Good:

```text
Cannot attach fentry to foo_get: function is not BTF-visible.
Retrying kprobe fallback...
```

## Documentation

Required:
- 10-minute quick start;
- mental model;
- target authoring guide;
- confidence model;
- "when RefScope is the wrong tool";
- troubleshooting;
- architecture;
- real case studies.

## External validation

v0.8 is not complete until at least one person who did not write the tool:

1. installs/builds it;
2. runs it on a real or supplied kernel bug;
3. obtains a useful report without live assistance.

Collect their friction points.

## Community process

Open:
- issue templates;
- bug-case submission template;
- contribution guide;
- target-adapter guide.

For kernel-facing design questions, seek feedback in appropriate BPF/tracing/kernel debugging communities.

Do not spam mailing lists with marketing.

## Integration opportunities

Evaluate, but do not force:

- retsnoop-compatible capture/source information;
- syzkaller/ktest orchestration;
- drgn postmortem helpers;
- machine-readable output for CI.

Prefer composition over replacing good existing tools.

## Acceptance criteria

- [ ] new user succeeds without author assistance;
- [ ] x86_64 and arm64 release path tested;
- [ ] schemas versioned and validated;
- [ ] deterministic offline diagnosis;
- [ ] no known data-corrupting event loss bug;
- [ ] external user feedback incorporated;
- [ ] at least 5 real bug case studies;
- [ ] several upstream fixes/reviews provide credibility;
- [ ] documentation explains limitations prominently;
- [ ] benchmark and compatibility matrix published.

## Promotion threshold

This is the point where broader promotion becomes rational:

- BPF/kernel debugging communities;
- technical blog;
- conference/meetup proposal;
- distro/package interest if it exists.

The message should still be evidence-first, not hype.
