# RefScope v0.3 — Real syzbot workflow and first upstream proof

## Purpose

Prove that RefScope is not a synthetic research toy.

This release is the most important milestone in the whole roadmap.

## Required outcome

At least one real Linux bug must go through:

```text
public bug report
→ reproducible locally
→ RefScope diagnosis
→ human-confirmed root cause
→ minimal fix
→ submitted upstream
```

Preferred release gate: fix is accepted/merged or receives maintainer confirmation.

## CLI goal

```bash
refscope syzbot <bug-id-or-report>
```

Do not attempt full automation immediately.

The command may orchestrate existing tools and require a prepared kernel tree.

## Required workflow stages

### Stage 1 — import report

Parse/store:
- bug title;
- report/log;
- kernel commit;
- tree;
- config;
- architecture;
- compiler;
- syz reproducer;
- C reproducer if available;
- existing bisection information.

Write:

```text
cases/<id>/input/
```

### Stage 2 — environment validation

Check:
- kernel tree commit matches;
- `.config` provenance;
- vmlinux exists;
- BTF/DWARF availability;
- VM architecture;
- sanitizer config;
- reproducer executable.

Do not silently analyze a different kernel build.

### Stage 3 — reproduce

Integrate with existing tooling where sensible.

Do not reinvent all of syzkaller or ktest.

Required result:

```text
N attempts
M reproduced failures
failure rate
median time-to-failure
```

### Stage 4 — identify target object

Initially this may be human-assisted.

Store:
- candidate struct;
- target config;
- crashing object pointer when observable;
- sanitizer report location;
- final put/free context when available.

### Stage 5 — collect runs

Collect:
- failing executions;
- good/non-failing executions if available;
- capture quality;
- crash report.

If no good execution exists, support one fallback:

#### Patched-vs-unpatched comparison
Once a candidate fix is known, compare runs to validate the diagnosis.

or:

#### Object-cohort comparison
Compare failing object lifetime to earlier normal instances in the same run.

### Stage 6 — diagnose

Generate:

```text
cases/<id>/analysis/refscope.json
cases/<id>/analysis/report.md
```

Report must contain:
- observed failure;
- target object;
- relevant acquisition(s);
- relevant release(s);
- first ownership divergence;
- top 3 candidates;
- confidence/evidence;
- source locations;
- limitations.

### Stage 7 — human verification

A human must inspect source and state:

```text
confirmed root cause: yes/no
```

Store verification notes.

RefScope does not auto-submit patches.

### Stage 8 — fix evidence

Store:
- patch;
- before/after reproduction counts;
- link/reference to upstream submission;
- review status.

## Case study format

Every successful real bug gets:

```text
cases/<bug>/
├── README.md
├── input/
├── target.yaml
├── analysis/
├── fix/
└── reproduce.sh
```

README sections:

1. Original failure.
2. What existing report told us.
3. What RefScope observed.
4. Root-cause hypothesis.
5. Source verification.
6. Fix.
7. Upstream status.
8. Time/effort comparison.

## Required case count

For v0.3 release:

Minimum:
- 3 real attempted bugs;
- at least 1 successful meaningful diagnosis.

Strong v0.3:
- 3 successful diagnoses;
- at least 1 merged/accepted fix.

## Baseline comparison

For each successful case compare against:

- sanitizer report alone;
- source reading;
- optional retsnoop/manual tracing;
- subsystem-native reference trace if it exists.

Measure:

```text
time to first correct root-cause hypothesis
manual commands/iterations required
amount of trace output manually inspected
```

Exact scientific rigor is not required, but the comparison must be honest.

## Failure taxonomy

Document cases where RefScope fails:

- bug stops reproducing when traced;
- no observable wrapper;
- object identity unavailable;
- no useful comparison cohort;
- event loss;
- unrelated race dominates;
- ownership semantics too ambiguous.

This section is essential for credibility.

## Acceptance criteria

- [ ] 3 public real bugs attempted and archived;
- [ ] at least 1 bug receives a correct source-level diagnosis;
- [ ] diagnosis is produced before or independently of simply copying an existing patch;
- [ ] one minimal Linux patch is submitted;
- [ ] before/after reproduction is documented;
- [ ] failed cases are published, not hidden;
- [ ] `refscope syzbot` reduces repetitive setup work;
- [ ] report is understandable without reading raw event logs.

## Kill criterion after v0.3

Seriously consider stopping/pivoting if:

- 5+ appropriate reproducible lifetime bugs were attempted;
- RefScope never beat manual KASAN + source reading + retsnoop/ref_tracker;
- no maintainer/researcher expresses interest in the diagnostic output;
- each new case requires substantial custom instrumented kernel changes.

## Public release strategy

This is the first version worth actively promoting.

Announcement should lead with evidence:

```text
RefScope helped localize <real bug> to <specific missing/extra reference path>.
Resulting fix: <upstream submission>.
```

Not:
- "AI-powered revolutionary debugger";
- stars;
- LOC;
- architecture diagram with no real case.

## What you gain if v0.3 succeeds

Even if the project stops here, you now have:

- a nontrivial Linux/BPF debugger;
- a reproducible real-kernel case study;
- at least one upstream patch;
- a credible reason for kernel developers to look at the repository.

That alone makes the experiment worthwhile.
