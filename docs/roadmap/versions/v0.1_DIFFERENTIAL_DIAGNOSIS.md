# RefScope v0.1 — Differential Diagnosis

## Purpose

This is the first version that contains the project's actual differentiator.

RefScope must compare successful and failing executions and produce a **small ranked set of ownership/reference divergences**.

If v0.1 only prints a bigger timeline, the project has failed its thesis.

## Core user flow

Record successful executions:

```bash
refscope record \
  --target targets/foo.yaml \
  --label good \
  -- ./repro --mode=no-trigger
```

Record failing executions:

```bash
refscope record \
  --target targets/foo.yaml \
  --label bad \
  -- ./repro
```

Diagnose:

```bash
refscope diagnose runs/
```

Output:

```text
Likely reference-lifetime divergence

Object class: struct foo
Confidence: STRONG

Acquisition:
  foo_get()
    foo_queue()
    submit_request()

Observed in:
  49/50 good runs
  1/50 bad runs

Good path:
  foo_fail()
  → foo_put()

Failing path:
  foo_fail()
  → return -ENOMEM

Candidate:
  missing foo_put() on error path

Source:
  drivers/foo/bar.c:417
```

## Inputs

At minimum:
- 1 good run;
- 1 bad run.

Recommended:
- 10+ runs in each class.

Bad/good classification may initially be manual (`--label`).

Automatic crash detection is v0.3.

## Event representation for comparison

Represent each object lifetime as a sequence of semantic tokens:

```text
(op_type, normalized_function, normalized_stack, reason, return_class)
```

Examples:

```text
GET|foo_get|stack#31|WORK|-
PUT|foo_put|stack#42|WORK|-
CALL_RETURN|foo_fail|stack#8|-|-ENOMEM
```

## Alignment algorithm

v0.1 does not require a novel ML model.

Implement a deterministic alignment algorithm first.

Candidate methods:
- longest common subsequence;
- Myers diff;
- sequence alignment with domain-specific costs.

Costs should prefer:
- same operation type;
- same semantic reason;
- same stack fingerprint;
- same source function.

Do not align purely by timestamp.

## Cohort construction

Group comparable object lifetimes by:
- target type;
- initial acquisition stack;
- optional creation stack;
- semantic reason set;
- approximate control-flow context.

Avoid comparing unrelated objects merely because they share a struct type.

## First meaningful divergence

Define divergence as the earliest aligned point where:

- one side has an extra GET/PUT;
- reason changes;
- call path returns early;
- free occurs earlier/later;
- lifetime terminates on one side only.

The report must show a narrow window, e.g. 3–10 events before/after divergence.

## Candidate root-cause rules

Implement explicit rules before any ML.

### Rule 1 — unmatched acquisition
Good runs consistently show:

```text
GET X → ... → PUT X
```

Bad runs show:

```text
GET X → ... → end/error
```

Candidate: missing release.

### Rule 2 — extra release
Bad runs have an extra PUT relative to stable good sequence.

Candidate: double put / premature release.

### Rule 3 — early final release
Bad run reaches free/final-put before a later use path.

Candidate: premature release.

### Rule 4 — ownership transfer divergence
Good runs transition through known async handoff reason/path; bad run skips receiving-side acquisition or releasing-side cleanup.

Candidate: broken transfer.

### Rule 5 — error-path divergence
Bad-only negative return/branch appears immediately before balance differs.

Candidate source location receives ranking boost.

## Ranking

Each candidate gets a score from documented features, for example:

```text
+3 operation mismatch is unique
+3 appears in >80% good runs
+2 same acquisition stack across cohorts
+2 divergence adjacent to error return
+2 actual refcount confirms imbalance
+2 semantic reason matches
-2 capture had dropped events
-2 generation uncertain
-3 multiple equivalent candidates
```

Expose score components in JSON.

Do not hide ranking behind an opaque LLM.

## Confidence classes

### EXACT
Only if explicit per-reference identity proves it.

### STRONG
Deterministic differential evidence plus stable repeated runs.

### INFERRED
Statistical/heuristic match with multiple possibilities.

## Report formats

Required:
- human text;
- JSON.

Optional:
- Markdown case-study output.

JSON must contain:
- candidate list;
- evidence;
- confidence;
- run IDs;
- source locations;
- capture-quality warnings.

## Synthetic test suite

Create injected bug patterns:

1. missing PUT on error path;
2. double PUT;
3. early free;
4. async transfer missing receive-side GET;
5. noisy irrelevant object;
6. pointer reuse;
7. good and bad paths with different unrelated work;
8. event drop simulation.

For each bug, expected top-1 or top-3 candidate is specified.

## Accuracy requirement

For the synthetic suite:

- top-1 correct ≥ 80%;
- top-3 correct = 100%;
- zero false "EXACT" claims.

These numbers can be adjusted only with written justification.

## RxRPC validation

Use a subsystem with existing semantic reasons to check whether the sequence alignment preserves useful distinctions.

RefScope must not merely restate the native trace. It should demonstrate that the differential engine can infer the intentionally injected/known divergence.

## Acceptance criteria

- [ ] good/bad run bundles can be compared offline;
- [ ] object cohorts are not naively mixed;
- [ ] sequence alignment is deterministic;
- [ ] top candidates include source-level evidence;
- [ ] confidence class is always emitted;
- [ ] capture-quality warnings reduce confidence;
- [ ] injected missing-put bug is top-1;
- [ ] injected double-put bug is top-1;
- [ ] top-3 synthetic correctness reaches 100%;
- [ ] a human report fits on roughly one terminal screen for the top candidate.

## Out of scope

- automatically downloading syzbot bugs;
- automatic patch generation;
- support for every refcount implementation;
- neural ranking;
- production always-on tracing.

## Release gate

v0.1 is worth publishing publicly only if the demo is:

```text
reproducer
→ two run classes
→ short explanation of the exact injected/known faulty path
```

not:

```text
10,000 events
→ user figures it out manually
```

## Go/no-go

If this version cannot reliably shrink a known lifetime bug to a specific path/candidate, **do not continue adding integrations**. Fix the diagnosis model or stop.
