# RefScope v0.2 — Reference Provenance and Target Discovery

## Purpose

Reduce the amount of hand-written target configuration and make RefScope understand where reference semantics come from.

This is where RefScope starts becoming a reusable tool instead of a per-bug script.

## Design principle

Do not promise "automatic universal get/put discovery".

The kernel has:
- inline refcount operations;
- custom wrappers;
- kref;
- percpu_ref;
- atomic-based legacy counters;
- ownership transfers not represented by a single API call.

v0.2 must instead implement **evidence sources** and a confidence model.

## Evidence sources

### 1. Explicit target specification
Highest practical reliability.

```yaml
type: struct foo
operations:
  - function: foo_get
    role: acquire
    object: arg0
    reason: arg1
```

### 2. Existing subsystem tracepoints
If a tracepoint already emits:
- object identity;
- refcount;
- semantic reason;

prefer it over a weaker probe.

### 3. `ref_tracker`
If the target subsystem uses Linux reference tracker tokens, ingest them and mark those reference identities as `EXACT`.

### 4. BPF kfunc metadata
BTF/kfunc metadata can mark some functions with acquire/release semantics (`KF_ACQUIRE`, `KF_RELEASE`) for BPF-visible objects.

Use when applicable; do not assume it covers ordinary kernel code generally.

### 5. Symbol/name heuristics
Names like:
- `*_get`;
- `*_put`;
- `*_hold`;
- `*_release`;

are candidates only.

Never mark semantic role as exact from name alone.

### 6. Optional source analysis
When kernel source/compile database is available, scan functions for:
- `refcount_inc*`;
- `refcount_dec*`;
- `kref_get*`;
- `kref_put*`;
- `percpu_ref_get*`;
- `percpu_ref_put*`.

Produce candidate wrapper functions and the object field/argument data flow.

This may be implemented via:
- Clang AST tooling;
- LLVM IR analysis;
- a simpler source-index pass initially.

The result is suggestions, not ground truth.

## Target inspector CLI

```bash
refscope inspect-target \
  --type 'struct foo' \
  --kernel-tree ~/linux \
  --vmlinux ~/linux/vmlinux
```

Output:

```text
Candidate acquire APIs:
  foo_get(struct foo *)        STRONG
  foo_lookup(...) -> foo *     INFERRED

Candidate release APIs:
  foo_put(struct foo *)        STRONG

Refcount field:
  struct foo.refs              inferred from source/BTF

Existing tracepoints:
  foo:foo_ref                  available
```

## Target file generation

```bash
refscope inspect-target ... --write-target targets/foo.yaml
```

Generated file must include comments/metadata saying which entries were inferred.

Example:

```yaml
operations:
  - function: foo_get
    role: acquire
    object: arg0
    evidence:
      source_refcount_op: true
      name_heuristic: true
    confidence: strong
```

## Reference identity model

Add:

```text
ReferenceEvidence {
  acquisition_event
  release_event?
  semantic_reason?
  token_id?
  acquisition_stack
  release_stack?
  confidence
}
```

Do not force a one-to-one pair when evidence is insufficient.

Represent unresolved references explicitly.

## Pairing

Pairing priority:

1. explicit tracker/token identity;
2. unique semantic reason with stable good-run behavior;
3. unique stack/path signature;
4. sequence/differential inference.

If multiple pairings have equal support, keep alternatives.

## Async ownership transfer annotations

Introduce target-level optional transfer semantics:

```yaml
transfers:
  - from: foo_queue_work
    to: foo_work_handler
    key: arg0
    kind: workqueue
```

v0.2 does not need fully automatic async causality.

It needs a clean data model that will allow it.

## Final-put support

If a kernel provides a usable final-put tracepoint, RefScope may consume it.

If not:
- use configured destructor/free events;
- use subsystem wrappers;
- report final-release observability as unavailable.

Never require an out-of-tree kernel patch for the default v0.2 workflow.

## Three target requirement

v0.2 must be validated on at least three structurally different target APIs, for example:

1. RxRPC-style get/put with semantic reasons;
2. a kref-based target;
3. a target using explicit `ref_tracker` or another strongly instrumented subsystem.

Do not choose three near-identical wrappers.

## Tests

### Discovery precision
For known targets, compare generated candidate list to manually reviewed ground truth.

Metrics:
- acquire API precision;
- release API precision;
- recall;
- false high-confidence candidates.

Most important:
- zero false `EXACT`.

### Pairing tests
- explicit token → exact pair;
- unique reason → strong pair;
- ambiguous same-reason references → unresolved/inferred;
- cross-thread transfer → not rejected merely because thread differs.

## Acceptance criteria

- [ ] target inspector emits candidate APIs and evidence;
- [ ] target YAML can be generated then manually edited;
- [ ] explicit/native semantic sources take priority over heuristics;
- [ ] unresolved references are represented honestly;
- [ ] confidence is attached to each provenance edge;
- [ ] at least 3 target styles work;
- [ ] no target requires editing core RefScope source to add simple wrapper semantics;
- [ ] source/BTF absence degrades gracefully to manual mode.

## Performance requirement

Target discovery happens offline and may be slower.

Runtime capture remains bounded by selected probes.

Do not attach to hundreds/thousands of candidate functions by default.

## Out of scope

- full whole-kernel static ownership proof;
- perfect automatic discovery;
- patch synthesis;
- kernel-wide always-on refcount instrumentation.

## Go/no-go gate

If adding a new subsystem still requires writing substantial C/BPF code rather than a target description, the abstraction is not good enough yet.
