# RefScope v0.5 — Generic lifetime/provenance engine

## Purpose

Move from "works on selected get/put wrappers" to "works on several real Linux lifetime models with reusable adapters".

v0.5 is justified only after v0.3 proves real value.

## Supported lifetime/refcount families

Required:

1. `refcount_t` through subsystem wrapper APIs.
2. `kref`.
3. explicit Linux `ref_tracker` integration where present.
4. at least one async ownership-transfer pattern.

Preferred:
5. `percpu_ref`.
6. selected custom counter adapter.

Do not advertise generic support for raw legacy `atomic_t` counters unless explicitly modeled.

## Target adapter architecture

Target specification must support:

```yaml
type: struct foo
identity:
  pointer: true
operations:
  ...
lifecycle:
  create:
  free:
transfers:
  ...
fields:
  refcount:
```

Adapters may supply custom extraction logic, but most new targets should be data/config driven.

## Async causality

Required models:

### Workqueue
Represent:

```text
producer owns ref
→ queue_work
→ worker starts
→ worker releases/transfers
```

### Timer
Represent scheduling/cancel/handler transitions when target declares them.

### RCU
At minimum distinguish:
- logical release;
- deferred reclamation;
- RCU callback/free.

Avoid labeling an RCU grace period as a leak.

## Ownership graph

Add internal graph representation:

Nodes:
- object lifetime;
- reference evidence;
- task;
- async work item;
- relevant function/path.

Edges:
- acquire;
- release;
- transfer;
- schedule;
- consume;
- final release.

CLI:

```bash
refscope graph <run> --object <id> --format dot
refscope graph <run> --object <id> --format json
```

Graph rendering itself is secondary. Graph semantics are core.

## Multi-object interactions

Support related object identities when a target declares relationships.

Example:

```text
connection → call → skb
```

Do not attempt global arbitrary pointer graph reconstruction.

## Better differential cohorts

Support:
- good vs bad labels;
- patched vs unpatched;
- same-run normal vs anomalous instances;
- clustering by creation/acquisition stack.

Use robust statistics:
- event frequency;
- path frequency;
- lifetime duration distribution;
- ref-balance distribution.

## Diagnosis rules

Expand beyond v0.1:

- missing release;
- extra release;
- early final put;
- missing acquisition before handoff;
- cleanup skipped on error;
- duplicate cleanup;
- async cancellation race signature;
- lifetime persists after all known owners exit.

Each rule must cite concrete evidence.

## Portability

Required:
- x86_64;
- arm64.

Test against:
- current mainline/development kernel used by project;
- at least one recent stable/LTS-style kernel if required BPF features exist.

Capability-based fallback is preferred to version-number branching.

## Regression corpus

Every fixed real bug becomes a permanent regression case.

Goal by v0.5:
- 5+ real cases;
- 3+ subsystems;
- at least 2 distinct refcount/lifetime models.

Tests should be runnable in VMs.

## Performance

Introduce benchmark suite:

1. synthetic high-rate get/put;
2. network workload with target probes;
3. async workqueue-heavy case.

Measure:
- runtime overhead;
- events/sec;
- drop rate;
- memory;
- reproduction-rate change with/without RefScope.

The last metric matters for race bugs.

## Required user experience

A new user should be able to:

```text
1. install/build RefScope
2. select/create a target
3. record runs
4. run diagnose
5. understand why confidence is limited
```

without reading the source.

## Acceptance criteria

- [ ] 3+ subsystems validated;
- [ ] `refcount_t` wrappers + kref + ref_tracker-supported target work;
- [ ] workqueue or timer transfer model works on a real case;
- [ ] x86_64 + arm64 CI/integration tests exist;
- [ ] 5+ real bug cases in regression corpus;
- [ ] at least 2 upstream fixes attributable in part to RefScope;
- [ ] graph model and JSON are stable enough for external tooling;
- [ ] new simple target requires config, not core code modification;
- [ ] performance/reproduction perturbation is documented.

## Things still out of scope

- every kernel object;
- formal proof;
- automatic patch submission;
- always-on fleet observability;
- cross-machine distributed tracing.

## Release narrative

At v0.5 the project should be described by its evidence, e.g.:

```text
Dynamic reference-provenance debugger for reproducible Linux lifetime bugs.
Validated on N real bugs across X/Y/Z subsystems.
```

If you cannot truthfully write that, v0.5 is premature.
