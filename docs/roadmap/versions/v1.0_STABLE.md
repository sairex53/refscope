# RefScope v1.0 — Stable release specification

## Definition of "stable"

Stable does **not** mean "feature complete".

It means:

1. documented supported scope;
2. stable machine-facing interfaces;
3. repeatable diagnostics;
4. compatibility discipline;
5. real external use;
6. proven value on real kernel bugs.

## Mandatory proof before tagging v1.0

Minimum evidence:

- 5+ real Linux lifetime/refcount bugs analyzed successfully;
- 3+ distinct subsystems;
- 2+ lifetime/refcount models;
- 2–3+ fixes accepted into upstream/maintainer trees or equivalent strong confirmation;
- at least 2 external users successfully run RefScope;
- at least 1 external user applies it to a bug/case not authored by you.

If these are missing, call it v0.x even if code quality is excellent.

## Stable CLI surface

Core commands:

```bash
refscope trace
refscope record
refscope timeline
refscope diagnose
refscope inspect-target
refscope graph
refscope syzbot
refscope doctor
```

`refscope doctor` prints compatibility/capabilities.

Breaking CLI changes after v1.0 require a documented migration/deprecation policy.

## Stable data formats

Freeze:

- `refscope.run.v1`;
- `refscope.target.v1`;
- `refscope.diagnosis.v1`.

Every format must include:
- schema version;
- RefScope version;
- kernel/build identity;
- target identity/hash;
- confidence/evidence metadata.

## Diagnosis contract

Every root-cause candidate includes:

```text
candidate ID
operation/lifetime class
source location
object lifetime ID
evidence list
counter-evidence
confidence
score breakdown
alternative candidates
capture quality warnings
```

Never output an unqualified "the bug is here" when evidence is inferred.

## Supported semantics

v1.0 must clearly list supported models.

Example:

```text
SUPPORTED
- configured get/put wrapper APIs
- kref through observable wrappers
- ref_tracker-backed exact references
- selected percpu_ref paths
- declared workqueue/timer transfers

PARTIAL
- custom refcount implementations
- RCU-heavy lifetimes

NOT GENERALLY SUPPORTED
- arbitrary pointer ownership
- formal verification
- races that stop reproducing under tracing
```

## Backend architecture

Capture and analysis must be separable.

```text
CaptureBackend
  → versioned run events
  → AnalysisEngine
```

This allows future backends:
- libbpf live tracing;
- native tracepoints;
- saved traces;
- possibly external tracer adapters.

The analysis engine must work offline.

## Robustness

### No kernel crash guarantee
The project cannot mathematically guarantee kernel tracing never triggers kernel bugs, but RefScope itself must:

- avoid unsafe arbitrary dereference;
- use verifier-safe BPF;
- bound resources;
- detect unsupported contexts;
- document tracing risks.

### Process robustness
- signal-safe cleanup;
- no orphaned pinned objects unless requested;
- corrupted run files produce errors, not undefined behavior;
- partial data remains analyzable with warnings.

## Performance

Publish reproducible benchmarks and hardware/kernel details.

Requirements:
- no silent drops;
- bounded memory;
- user can trade fidelity for overhead;
- target-specific reproduction-rate impact measured.

A debugging tool does not need production always-on overhead.

It does need to avoid making most target bugs impossible to reproduce.

## Compatibility

Policy:
- current mainline/development kernel: best support;
- selected recent stable kernels: tested;
- unsupported older kernels: explicit.

Prefer runtime capability probing.

## Testing bar

Required CI categories:

1. userspace unit tests;
2. BPF verifier/build tests;
3. VM integration tests;
4. architecture matrix;
5. schema compatibility tests;
6. synthetic lifetime-bug suite;
7. selected real regression cases.

Before a release:
- all mandatory tests pass;
- known diagnosis changes reviewed against regression corpus.

## Documentation bar

Required:
- quick start;
- complete CLI reference;
- target schema;
- data schema;
- architecture;
- confidence model;
- real case studies;
- limitations;
- troubleshooting;
- contribution guide;
- benchmark methodology.

## Project governance

At minimum:
- issue labels for target support / diagnosis bug / capture bug;
- release changelog;
- security reporting path for vulnerabilities in the tool;
- review requirements for changes to scoring/confidence semantics.

## v1.0 success criteria after release

A successful v1.0 is not defined by downloads.

Strong signals:
- kernel developers reference RefScope output in bug discussion;
- a bug is fixed by someone other than you using the tool;
- subsystem target descriptions are contributed externally;
- integration with another debugging/fuzzing workflow appears organically.

## What you will actually have built

If this specification is met, RefScope is no longer a portfolio demo.

It is:

> a practical dynamic reference-provenance and differential lifetime debugger for a documented subset of Linux kernel bugs, with real upstream case studies and stable interfaces.

That is a meaningful contribution even if it never becomes a default kernel tool.

## What v1.0 still does not promise

- universal automatic root-cause correctness;
- support for all kernel objects;
- zero overhead;
- fame;
- widespread adoption;
- replacement of KASAN, ref_tracker, retsnoop, drgn, syzkaller, or static analyzers.

Its job is to compose the missing evidence and shorten one expensive class of debugging work.
